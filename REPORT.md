## 3. Постановка задачі

**Формат запису** (поля розділені `;`, файл у UTF-8, без заголовка):

```text
id;weightKg;city;deliveryDays;express
```

| Поле | Тип | Правила перевірки |
|------|-----|-------------------|
| id | String | не порожнє |
| weightKg | double | число з крапкою, не від'ємне |
| city | String | не порожнє |
| deliveryDays | int | ціле число, не від'ємне |
| express | boolean | лише `true` або `false` |

**Чотири показники варіанта 15:**

1. кількість коректних записів;
2. середня вага (кг);
3. найбільший термін доставлення (дн.);
4. кількість експрес-доставлень.

Хибний рядок не завершує програму аварійно: він пропускається, а в звіті вказано номер рядка та причину. Хибний рядок не впливає на показники.

## 4. Структура програми

```text
src/main/java/ua/lpnu/kzp/
├── Main.java          — точка входу, розбір аргументів
├── FileReport.java    — читання та запис файлів (Path, UTF-8)
└── ParcelReport.java  — перевірка, обчислення, формування тексту звіту
```

**Потік даних:**

```text
data/input.csv
      ↓  FileReport.readLines
  List<String>
      ↓  ParcelReport.buildReport
 (перевірка → перетворення → обчислення → текст звіту)
      ↓
    String report
   ↙          ↘
консоль   FileReport.writeReport → out/report.txt
```

Логіка обчислення не дублюється: один метод `buildReport` формує текст, який потім виводиться у два місця.

**Параметри командного рядка:** `--help`, `--version`, `--input <файл>`, `--output <файл>`. За замовчуванням вхід `data/input.csv`, вихід `out/report.txt`.

## 5. Інфраструктура

**Maven (`pom.xml`).** Координати `ua.lpnu.kzp:lab01:1.0.0`, `maven.compiler.release` = 21, кодування UTF-8.

| Компонент | Версія | Призначення |
|-----------|--------|-------------|
| junit-jupiter | 5.12.2 (scope `test`) | тести |
| maven-compiler-plugin | 3.13.0 | компіляція |
| maven-surefire-plugin | 3.5.2 | запуск тестів |
| spotbugs-maven-plugin | 4.9.7.0 (фаза `verify`) | статичний аналіз байт-коду |
| maven-shade-plugin | 3.6.0 (фаза `package`) | виконуваний JAR із залежностями |

**Maven Wrapper** згенеровано командою `mvn wrapper:wrapper`. Файли `mvnw`, `mvnw.cmd` і `.mvn/` зберігаються в репозиторії, тому після цього глобальний Maven не потрібен.

**Версія.** `Implementation-Version` у маніфесті JAR береться з `${project.version}`, її виводить `--version`.

**GitHub Actions** (`.github/workflows/ci.yml`): матриця `ubuntu-latest`, `windows-latest`, `macos-latest`, JDK 21 (Temurin) з кешем Maven, виконання `./mvnw -B clean verify` (на Windows `mvnw.cmd`), публікація JAR як артефакту з назвою `jar-<ос>-<номер запуску>`.

## 7. Приклади роботи

**Вхідні дані** (`data/input.csv`):

```text
P001;2.5;Львів;2;true
P002;10.0;Київ;4;false
P003;0.8;Одеса;3;true
P004;abc;Харків;5;false
P005;-3.0;Дніпро;2;true
;4.0;Львів;3;false
P007;1.5;Львів
P008;3.2;Тернопіль;3;maybe
```

Три перші рядки коректні, п'ять останніх перевіряють різні види помилок.

**Консольний вивід:**

```text
Коректних записів: 3
Середня вага: 4.43 кг
Найбільший термін: 4 дн.
Експрес-доставлень: 2
Помилок: 5
Рядок 4: числове поле має помилковий формат
Рядок 5: від'ємне числове значення
Рядок 6: порожній id або місто
Рядок 7: очікується 5 полів, отримано 3
Рядок 8: express має бути true або false
```

**Файл звіту** `out/report.txt` містить той самий текст у UTF-8.

**Перевірка середньої ваги:** (2.5 + 10.0 + 0.8) / 3 = 13.3 / 3 ≈ 4.43.

**Запуск `--version`:**

```text
lab01 1.0.0
```

**Нюанс Windows.** У консолі з кодуванням за замовчуванням літера «і» могла відображатися як `?`. Файл звіту при цьому був коректним, бо записується в UTF-8. Вирішено командою `chcp 65001` перед запуском.

## 11. Відповіді на контрольні питання

1. **Призначення `pom.xml`.** Це опис Maven-проєкту: координати, версія Java, кодування, залежності й плагіни. За ним Maven знає, як компілювати, тестувати, перевіряти й пакувати програму.

2. **`test`, `verify`, `package`.** `test` компілює й запускає тести. `verify` виконує все попереднє та додаткові перевірки (у нас SpotBugs). `package` після цього створює JAR.

3. **Maven Wrapper.** Скрипти `mvnw` і `mvnw.cmd` завантажують потрібну версію Maven, тому на кожному комп'ютері не потрібна однакова глобальна установка.

4. **Метод `main`.** Це точка входу: з нього JVM починає виконання програми.

5. **Примітивний тип проти `String`.** Примітив (`int`, `double`, `boolean`) зберігає саме значення. `String` є посилальним типом: змінна містить посилання на об'єкт із текстом.

6. **Середнє в `double`.** Ділення двох `int` відкидає дробову частину. Приведення `(double) total / count` зберігає її.

7. **`Integer.parseInt("abc")`.** Метод кидає `NumberFormatException`, бо рядок не є числом. У програмі його перехоплюють на рівні одного рядка.

8. **Чому не можна мовчки пропускати помилку.** Користувач має знати, чому запис не потрапив до розрахунків, тому виводиться номер рядка й причина.

9. **`split(";", -1)`.** Від'ємний другий аргумент зберігає порожні поля наприкінці рядка, тому кількість полів визначається правильно.

10. **`Path.of`.** Він сам підставляє правильний роздільник для Windows, macOS та Ubuntu, на відміну від жорстко записаного `"data\\input.csv"`.

11. **Явний UTF-8.** Стандартне кодування залежить від системи. Явне UTF-8 гарантує однакове читання українських символів скрізь.

12. **`%n` та `\n`.** `%n` дає роздільник рядка поточної ОС (`\r\n` у Windows, `\n` в Unix), а `\n` завжди один символ.

13. **Що перевіряється у варіанті 15.** Кількість полів (5), непорожні `id` та `city`, `weightKg` як невід'ємне число, `deliveryDays` як невід'ємне ціле, `express` лише `true` або `false`.

14. **Тести для середнього.** Тест із кількома записами та відомим результатом: вага 2.5, 10.0 та 0.8 дають середнє 4.43. Також тест без коректних записів, щоб не було ділення на нуль.

15. **Статичний аналізатор.** SpotBugs шукає потенційні дефекти в байт-коді без запуску програми та зупиняє збірку, якщо знаходить проблему.

16. **GitHub Actions.** Автоматично збирає й перевіряє кожну зміну на Windows, macOS та Ubuntu та публікує JAR як артефакт.

## 5. Реалізація

### 5.1. Клас-сутність `Parcel`

У лабораторній № 1 метод `ParcelReport.buildReport()` самостійно розбирав CSV та накопичував статистику в окремих змінних (`validCount`, `totalWeight`, `maxDays`, `expressCount`). Після рефакторингу кожен коректний запис представлено об’єктом `Parcel`.

```java
public final class Parcel {
    private final String id;
    private final double weightKg;
    private final String city;
    private final int deliveryDays;
    private final boolean express;
}
```

Клас оголошено `final`, поля — `private final`, а сеттери відсутні. Читання значень забезпечують методи `getId()`, `getWeightKg()`, `getCity()`, `getDeliveryDays()` та `isExpress()`.

### 5.2. Перевірка інваріантів

Конструктор не допускає порожні `id` і `city`, від’ємні вагу та термін, а також `NaN` і `Infinity` для ваги. При порушенні вимог генерується `IllegalArgumentException`.

```java
if (id == null || id.isBlank() || city == null || city.isBlank()) {
    throw new IllegalArgumentException("порожній id або місто");
}
if (!Double.isFinite(weightKg)) {
    throw new IllegalArgumentException("числове поле має помилковий формат");
}
if (weightKg < 0 || deliveryDays < 0) {
    throw new IllegalArgumentException("від'ємне числове значення");
}
```

Поле `express` має тип `boolean`, тому окремого інваріанта не потребує: коректність його текстового запису (`true` або `false`) перевіряє `fromCsv()`.

### 5.3. Фабричний метод `fromCsv()`

Метод `Parcel.fromCsv()` перевіряє, чи рядок не порожній, розділяє його за `;` (`split(";", -1)`), перевіряє наявність п’яти полів, перетворює числові значення та перевіряє `express`. `NumberFormatException` перетворюється на `IllegalArgumentException`. Після розбору викликається основний конструктор `Parcel`, тому правила предметної області не дублюються: `fromCsv()` відповідає за структуру CSV, а конструктор — за коректність стану об’єкта.

```java
Parcel parcel = Parcel.fromCsv("P001;2.5;Lviv;3;true");
```

### 5.4. Допоміжний `record WeightDelivery`

`WeightDelivery` зберігає вагу й термін як незмінну пару значень. Його компактний конструктор перевіряє коректність числових полів.

```java
public WeightDelivery toWeightDelivery() {
    return new WeightDelivery(weightKg, deliveryDays);
}
```

### 5.5. Шаблон `Parcel.Builder`

Реалізовано `Parcel.Builder` для зручнішого створення посилок. Метод `build()` використовує основний конструктор `Parcel`, тому Builder не обходить перевірки коректності.

### 5.6. `toString()` та `Locale.ROOT`

Метод `toString()` використовує `String.format(Locale.ROOT, ...)`, щоб формат десяткових чисел не залежав від локалі Windows, Ubuntu або macOS.

### 5.7. Обробка даних у `ParcelReport`

Кожен CSV-рядок обробляється через `Parcel.fromCsv()`. Коректні об’єкти додаються до `List<Parcel>`. Для некоректного рядка формується повідомлення `Рядок N: причина`; такий запис не впливає на статистику.

  → ParcelReport.buildReport

  → перевірка в конструкторі Parcel

## 11. Завдання із зірочкою

### 11.1. Забезпечення незмінності класу Parcel

Клас `Parcel` реалізовано як `final`, а всі його поля оголошено `private final`. Після створення об’єкта його стан не може бути змінений. Методи для зміни значень полів (`setter`) відсутні. Перевірка коректності значень виконується в основному конструкторі класу.

### 11.2. Реалізація Parcel.Builder

Для зручного створення об’єктів реалізовано вкладений клас `Parcel.Builder`. Шаблон Builder дозволяє послідовно задавати значення полів посилки та створювати об’єкт за допомогою методу `build()`.

```java
Parcel parcel = Parcel.builder()
        .id("P001")
        .weightKg(2.5)
        .city("Lviv")
        .deliveryDays(2)
        .express(true)
        .build();
```

### 11.3. Використання основного конструктора

Метод `build()` створює об’єкт через основний конструктор `Parcel`. Таким чином, усі перевірки коректності значень виконуються незалежно від способу створення об’єкта. Builder не обходить валідацію.

### 11.4. Переваги незмінності під час багатопотокової роботи

Незмінність об’єктів `Parcel` зменшує ризик помилок під час передавання даних між потоками. Оскільки стан об’єкта після створення не змінюється, потоки не можуть одночасно змінювати його поля. Це усуває гонки даних, пов’язані зі зміною стану самого об’єкта, та спрощує використання посилок у багатопотокових програмах. Незмінність також полегшує тестування, налагодження та підтримку програмного коду.

- Валідація даних збережена.

## 12. Відповіді на контрольні питання

1. **Навіщо потрібен клас-сутність?**
   Він об’єднує пов’язані дані одного запису в один об’єкт. Замість окремих значень `id`, `weightKg`, `city`, `deliveryDays` та `express` програма працює з одним `Parcel`, і ризик переплутати значення зменшується.

2. **Що забезпечують модифікатори `private` і `final` для полів?**
   `private` закриває поле від прямого доступу ззовні класу, а `final` забороняє переприсвоювати його після створення об’єкта.

3. **Що таке інкапсуляція?**
   Це приховування внутрішнього стану об’єкта та доступ до нього лише через визначені методи (getter-и). Клас сам контролює, які значення можуть потрапити в його поля.

4. **Чому перевірку інваріантів виконують у конструкторі?**
   Конструктор — єдина точка створення об’єкта. Якщо перевірка там, то некоректний `Parcel` неможливо створити взагалі, а не потрібно перевіряти його перед кожним використанням.

5. **Чим відрізняється перевірка на `null` від `isBlank()`?**
   Перевірка на `null` виявляє відсутній рядок, а `isBlank()` — порожній рядок або рядок, що складається лише з пробілів. Для `id` і `city` потрібні обидві.

6. **Чому в класі немає setter-ів?**
   Без setter-ів перевірений стан не можна змінити після створення, тож об’єкт залишається коректним протягом усього часу існування.

7. **Що автоматично створює `record`?**
   Компілятор створює конструктор, методи доступу до компонентів (наприклад, `weightKg()`), а також `equals()`, `hashCode()` і `toString()`.

8. **Коли доцільніше використати `record`, а коли звичайний клас?**
   `record` підходить для компактних незмінних наборів даних, як `WeightDelivery`. Звичайний клас, як `Parcel`, потрібен, коли треба більше контролю: приватні поля, фабричний метод, Builder, власна поведінка.

9. **Чи завжди `record` повністю незмінний?**
   Ні. Якщо компонент record містить змінний об’єкт (наприклад, змінну колекцію), його внутрішній стан усе одно можна змінити. У `WeightDelivery` компоненти примітивні, тому він незмінний.

10. **Що робить метод `fromCsv()`?**
    Перетворює один CSV-рядок на готовий об’єкт `Parcel`: перевіряє структуру й числовий формат, а потім викликає конструктор.

11. **Де потрібно перехоплювати помилку одного CSV-рядка?**
    У циклі обробки (`ParcelReport.buildReport()`). Там `IllegalArgumentException` перетворюється на повідомлення `Рядок N: причина`, а програма продовжує обробляти наступні рядки.

12. **Чому некоректний запис не можна додавати до списку?**
    Інакше він потрапить у розрахунки й спотворить статистику (середню вагу, найбільший термін, кількість експрес-доставлень).

13. **Чим `toString()` відрізняється від CSV-формату?**
    `toString()` призначений для людини (наприклад, `Parcel{id=P001, ...}`), а CSV-рядок має суворо визначений формат із роздільником `;` для обміну даними.

14. **Навіщо використовувати `Locale.ROOT`?**
    Щоб дробові числа форматувалися однаково (з крапкою) незалежно від мови й регіональних налаштувань операційної системи.

15. **Що означає схема AAA у тестах?**
    Arrange — підготовка даних, Act — виконання дії, Assert — перевірка результату.

16. **Що потрібно перевірити в тестах конструктора?**
    Коректні значення, `null` і порожні `id` та `city`, від’ємні вагу й термін, `NaN`, `Infinity` та граничні значення (`0`).

## 4. Базовий тип Parcel

Parcel реалізовано як абстрактний базовий клас.

Спільні поля:

```java
private final String id;
private final double weightKg;
private final String city;
private final int deliveryDays;
private final boolean express;
```

Для всіх підтипів встановлено спільні правила:

- id не може бути null або порожнім;
- city не може бути null або порожнім;
- вага посилки не може бути від'ємною;
- термін доставлення не може бути від'ємним;
- вага повинна бути скінченним числовим значенням.

Перевірка числових значень виконується за допомогою:

```java
Double.isFinite(weightKg)
```

Спільна валідація виконується в конструкторі базового класу.

У класі Parcel оголошено абстрактні методи:

```java
public abstract DeliveryKind getDeliveryKind();

public abstract int calculateDeliveryTime();

public abstract double calculateDeliveryCost();
```

Абстрактний клас використано замість інтерфейсу, оскільки підтипи мають спільні поля, правила перевірки та частину готової реалізації.

RegularParcel і ExpressParcel є різновидами Parcel, тому між ними існує відношення is-a.

Допоміжний record WeightDelivery не є різновидом посилки. Він використовується для збереження ваги та терміну доставлення як окремого незмінного значення.

Також збережено функціональність попередньої лабораторної роботи:

- getter-и;
- метод fromCsv();
- метод toString();
- метод toWeightDelivery();
- шаблон проєктування Builder.

Методи fromCsv() та Builder.build() створюють відповідний підтип посилки залежно від виду доставлення.

## 5. Підтипи

Створено два підтипи:

```text
RegularParcel
ExpressParcel
```

### RegularParcel

Клас RegularParcel представляє звичайне доставлення посилки.

Конструктор:

```java
public RegularParcel(String id, double weightKg,
                     String city, int deliveryDays) {
    super(id, weightKg, city, deliveryDays, false);
}
```

Розрахунок терміну доставлення:

```java
@Override
public int calculateDeliveryTime() {
    return getDeliveryDays();
}
```

Розрахунок вартості:

```java
@Override
public double calculateDeliveryCost() {
    return 50.0 + getWeightKg() * 10.0;
}
```

Базова вартість звичайного доставлення становить 50 грн, а за кожен кілограм ваги додається 10 грн.

### ExpressParcel

Клас ExpressParcel представляє експрес-доставлення посилки.

Конструктор:

```java
public ExpressParcel(String id, double weightKg,
                     String city, int deliveryDays) {
    super(id, weightKg, city, deliveryDays, true);
}
```

Розрахунок терміну доставлення:

```java
@Override
public int calculateDeliveryTime() {
    return Math.max(0, getDeliveryDays() - 1);
}
```

Розрахунок вартості:

```java
@Override
public double calculateDeliveryCost() {
    return 100.0 + getWeightKg() * 20.0;
}
```

Експрес-доставлення скорочує початковий термін доставлення на один день. Метод Math.max() не дозволяє отримати від'ємне значення.

Базова вартість експрес-доставлення становить 100 грн, а за кожен кілограм ваги додається 20 грн.

### Приклад розрахунку

Для посилки вагою 2.5 кг із початковим терміном доставлення 2 дні:

| Показник | RegularParcel | ExpressParcel |
|---|---:|---:|
| Вага, кг | 2.5 | 2.5 |
| Термін доставлення, дні | 2 | 1 |
| Вартість доставлення, грн | 75 | 150 |

## 7. equals() і hashCode()

У базовому класі Parcel реалізовано узгоджені методи:

```java
equals()
hashCode()
```

Під час визначення логічної рівності враховуються:

- конкретний клас об'єкта;
- ідентифікатор посилки;
- вага;
- місто доставлення;
- термін доставлення;
- ознака експрес-доставлення.

Реалізація equals():

```java
@Override
public final boolean equals(Object obj) {

    if (this == obj) {
        return true;
    }

    if (obj == null || getClass() != obj.getClass()) {
        return false;
    }

    Parcel other = (Parcel) obj;

    return Double.compare(weightKg, other.weightKg) == 0
            && deliveryDays == other.deliveryDays
            && express == other.express
            && id.equals(other.id)
            && city.equals(other.city);
}
```

Реалізація hashCode():

```java
@Override
public final int hashCode() {
    return Objects.hash(
            getClass(),
            id,
            weightKg,
            city,
            deliveryDays,
            express
    );
}
```

Обидва методи оголошено як final, що забезпечує єдині правила рівності для всіх підтипів.

Об'єкти різних підтипів не вважаються рівними навіть за однакових спільних характеристик.

Коректність реалізації перевірено через:

```java
HashSet<Parcel>
```

Два логічно рівні об'єкти не утворюють дублікати в множині HashSet.

## 14. Відповіді на контрольні питання

### 1. Для чого потрібен базовий тип?

Базовий тип дозволяє об'єднати спільні характеристики та методи декількох споріднених класів. У цьому проєкті Parcel зберігає загальні дані посилки та правила їх перевірки, завдяки чому не потрібно повторювати однаковий код у підтипах.

### 2. Чим відрізняються extends та implements?

Ключове слово extends встановлює відношення спадкування між класами. Implements використовується для реалізації методів, передбачених контрактом інтерфейсу.

### 3. Для чого використовується abstract?

Abstract дозволяє визначити загальний клас, для якого не передбачено безпосереднього створення об'єктів. Абстрактні методи задають операції, конкретну реалізацію яких повинні надати підтипи.

### 4. Для чого використовується super(...)?

Super(...) забезпечує виклик конструктора батьківського класу. У RegularParcel та ExpressParcel через нього передаються спільні характеристики посилки до конструктора Parcel.

### 5. Яке призначення анотації @Override?

Анотація @Override вказує, що метод підтипу перевизначає успадкований метод. Вона допомагає виявити помилки в назві, параметрах або сигнатурі методу під час компіляції.

### 6. Що таке поліморфізм?

Поліморфізм дає можливість використовувати об'єкти різних класів через один спільний тип. Конкретна реалізація методу вибирається під час виконання програми залежно від фактичного типу об'єкта.

### 7. Коли доцільно використовувати абстрактний клас, а коли інтерфейс?

Абстрактний клас доцільний, коли об'єкти мають спільні поля, правила валідації та частину реалізованої поведінки. Інтерфейс використовують для визначення спільного контракту, який можуть реалізовувати навіть неспоріднені класи.

### 8. Чим відрізняються спадкування та композиція?

Спадкування означає, що один клас є конкретним різновидом іншого. Наприклад, ExpressParcel є різновидом Parcel. Композиція передбачає використання одного об'єкта як складової іншого без встановлення відношення спадкування.

### 9. Для чого використовується enum із полями та методами?

Enum дозволяє описати наперед визначений набір допустимих значень. За необхідності кожна константа може містити додаткові характеристики або поведінку. У цьому проєкті DeliveryKind представляє види доставлення посилок.

### 10. Чому значення enum можна порівнювати через ==?

Кожна константа enum представлена єдиним екземпляром відповідного типу. Тому оператор == дозволяє коректно визначити, чи посилаються дві змінні на однакову константу.

### 11. Який контракт повинні виконувати equals() і hashCode()?

Якщо equals() визначає два об'єкти як рівні, їхні хеш-коди повинні збігатися. Метод equals() має забезпечувати рефлексивність, симетричність, транзитивність, стабільність результату та повертати false при порівнянні з null.

### 12. Що відбудеться, якщо змінити поле ключа HashMap, яке впливає на hashCode()?

Після зміни такого поля новий хеш-код може не відповідати місцю, де ключ було збережено. У результаті операції пошуку або видалення можуть працювати некоректно. У класі Parcel поля є незмінними, що дозволяє уникнути цієї проблеми.

### 13. Чому об'єкти різних підтипів можуть бути нерівними?

Навіть за однакових спільних характеристик різні підтипи можуть мати відмінну поведінку та логічне призначення. Тому в equals() додатково перевіряється конкретний клас об'єкта за допомогою getClass().

### 14. Як працює поліморфна колекція?

Колекція базового типу може містити екземпляри декількох його підтипів. Наприклад, List<Parcel> підтримує збереження RegularParcel та ExpressParcel, а виклик методів виконується відповідно до типу кожного об'єкта.

### 15. Як довести, що підтипи мають різну поведінку?

Необхідно створити об'єкти різних підтипів з однаковими початковими характеристиками та викликати їхні поліморфні методи через базовий тип. Різні результати обчислення вартості та терміну доставлення підтверджують відмінність реалізацій.

### 16. Як перевірити коректність рівності через HashSet?

Потрібно створити два окремі, але логічно рівні об'єкти та додати їх до HashSet. Якщо equals() і hashCode() реалізовані правильно, множина міститиме лише один елемент.

### 17. Для чого використовуються sealed та permits?

Sealed дозволяє обмежити перелік класів, які можуть безпосередньо успадковувати базовий клас. Permits явно визначає такі класи. У цьому проєкті Parcel дозволяє спадкування лише RegularParcel та ExpressParcel.

### 18. Чому switch за підтипами не повинен дублювати логіку поліморфних методів?

Дублювання розрахунків у switch створює зайві залежності та ускладнює підтримку програми. Обчислення повинні залишатися в методах відповідних підтипів, а switch доцільно використовувати для окремих операцій, наприклад визначення текстового опису типу.

### 19. Що необхідно зберегти після перебудови об'єктної моделі?

Необхідно забезпечити сумісність із попереднім форматом CSV, зберегти перевірки попередніх автоматизованих тестів та контрольні показники звіту. Це дозволяє переконатися, що розширення моделі не порушило наявну функціональність.

### 20. Який фрагмент коду найкраще демонструє перевагу поліморфізму?

```java
Parcel parcel = new ExpressParcel(
        "P001", 2.5, "Львів", 2);

double cost = parcel.calculateDeliveryCost();
```

Змінна має базовий тип Parcel, проте викликаються реалізації методів класу ExpressParcel. Для цього не потрібно додатково перевіряти конкретний тип об'єкта.

## 15. Додаткове завдання — sealed-ієрархія

Для виконання додаткового завдання базовий клас Parcel оголошено як:

```java
public abstract sealed class Parcel
        permits RegularParcel, ExpressParcel {
```

Ключове слово sealed обмежує можливість спадкування базового класу.

Дозволені підтипи:

```text
RegularParcel
ExpressParcel
```

Обидва підтипи оголошено як final:

```java
public final class RegularParcel extends Parcel
```

```java
public final class ExpressParcel extends Parcel
```

Таким чином подальше спадкування від цих підтипів заборонено.

Для демонстрації pattern matching switch створено клас:

```java
ParcelTypeResolver
```

Метод визначення конкретного типу посилки:

```java
public static String describe(Parcel parcel) {

        case RegularParcel regular ->
                "Звичайне доставлення";

        case ExpressParcel express ->
                "Експрес-доставлення";
    };
}
```

У switch відсутня гілка default, оскільки компілятор знає всі дозволені підтипи sealed-ієрархії.

Після відновлення гілки ExpressParcel програма успішно скомпілювалася.
